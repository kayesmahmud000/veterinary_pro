# UXR-4 account recovery specification

Status: **Contract preparation complete; implementation not started.** This defines required behavior, not available endpoints or provider acceptance.
Date / inspected revision: **2026-10-22 / `a07d77f` plus existing local changes**.
Owners: [UXR-4](../../../apps/web/ROADMAP.md#uxr-4--complete-forgotten-password-recovery), [API-AUTH-R](../../../apps/api/ROADMAP.md#api-dependency-register). Execution/evidence: [plan](plan.md).

## Outcome, authority and scope

A person who forgot their password can request instructions through the existing sign-in modal, prove control of the account's registered email through a short-lived link, choose a replacement password and sign in normally. Preserve Bangla default/selectable English, the user's modal sign-in/sign-up requirement, platform roles, farm membership and existing login/onboarding returns.

This refines the broad authentication intent in the [blueprint, section 4](../../../vetralink_pro_blueprint.md) and dormant contracts from [Task 2.2](../../tasks/task-2.2-auth-dtos/spec.md). It extends the [auth-modal spec](../../tasks/web-auth-modals/spec.md), whose prohibition on dead recovery controls remains applicable until the implementation is accepted. SMS/OTP/passwordless login, authenticated change-password, email changes, MFA, lost-mailbox/manual recovery, impersonation and production rollout are outside this feature. Do not invent an unauthenticated support route; current own-support requires a session.

Primary perspectives: Backend/API and Application Security; Database/Tech Lead for transactions/workers; Frontend/UI/UX and QA for public forms; Release for migration, transport and hosting gates. The preparation stage writes these documents only.

## Decisions and alternatives

- Use opaque random email links and server-side single-use credentials. Stateless reset JWTs would still require consumption/revocation state; SMS/PIN and manual identity proof add unrelated providers/policy.
- Accept public requests into a durable, encrypted intake **before account lookup**. Eligible, absent and ineligible addresses follow the same HTTP/DB admission path; the worker later resolves eligibility. This avoids synchronous lookup/enqueue timing differences and crash loss. Do not claim perfectly constant network timing; verify distributions with controlled probes.
- Permit at most **six usable outstanding links per user**, enforced under the user lock independently of Redis. Count only unconsumed, uninvalidated, unexpired credentials matching current email/version. At the cap, skip/erase the new job without invalidating existing links; its public acknowledgement remains generic. A new request never revokes another valid link or any session. One successful reset invalidates all outstanding links. This limits request-driven denial of recovery.
- Use a dedicated SQL-polling worker, reusing established outbox/lease patterns without a second Redis business queue. Redis is used for abuse budgets only. This costs a durable worker deployment and two additive tables; it avoids recoverable secrets in queue payloads and retained failed-job collisions.
- Use the existing email/provider configuration but a recovery-specific Resend adapter with fixed error codes and a real/test result distinction. This keeps sensitive-send requirements out of unrelated order/role mail behavior. Test transport is allowed only through explicit nonproduction wiring.

## Public contracts — required, not implemented

API paths include the existing `/api/v1` prefix. Neither route takes a bearer session, role, farm, user ID, caller-provided reset URL or callback URL. Strict Zod plus Nest DTO validation; reject unknown keys, arrays and query parameters; JSON bodies at most **8 KiB by UTF-8 bytes**, including streamed/chunked requests.

| Method/path | Input | Successful `data` and status |
| --- | --- | --- |
| POST `/api/v1/auth/password-reset/request` | `{ email, locale? }`; email follows existing trimmed/lowercase/max-254/email validation; locale `bn` or `en`, default `bn`. | **202** `{ accepted: true }` for eligible, unknown, suspended, deleted and address-throttled requests. Means request received; never proves an account, queued mail or delivery. |
| POST `/api/v1/auth/password-reset/complete` | `{ token, newPassword }`; token exactly 64 lowercase hex characters; password 8–128 existing string code units and at most 72 UTF-8 bytes, with no trimming/normalization. | **200** `{ reset: true }`, only after committed password/session/audit mutation. No user summary, access/refresh token or automatic login. |

Use the normal response envelope once, with safe constant messages. Reuse/extend `ForgotPasswordRequestDto` with optional locale and retain `ResetPasswordRequestDto`'s existing fields. Add distinct strict acknowledgement/result schemas; do not reinterpret or remove the old unused `ForgotPasswordResponseDto` export. Password confirmation is client-only and never forwarded.

Errors: invalid JSON/unknown fields/date-independent field policy → 400/422 `VALIDATION_FAILED` with safe field identifiers, never submitted values; oversize → 413. Malformed, unknown, expired, consumed, invalidated, address-changed, version-changed or now-ineligible reset credentials → the same **400 `RESET_LINK_INVALID`** response. Validate new-password policy independently of account existence before lookup. Explicit IP/global/token abuse limits → 429 `RATE_LIMITED` plus a conservative `Retry-After`; limiter/storage/config/disabled-feature/queue-overload failures → account-independent 503 `RECOVERY_UNAVAILABLE`. No email-existence/status error. No GET validate/consume route.

Web mappings: POST `/api/auth/request-password-reset` → API request; POST `/api/auth/reset-password` → API complete. Exact method/path/body allowlists, same-origin JSON and cross-site rejection, bounded input, no forwarding of browser Authorization/unknown headers. Use private/no-store responses, `Referrer-Policy: no-referrer`; no credentials in path/query, cookies, HTML, logs or response. Browser result shapes are `{ accepted: true }`, `{ reset: true }`, or a bounded `{ code, fields? }` error; keep existing AuthResult/session behavior separate.

## Eligibility, credential and session lifecycle

Eligible means the submitted normalized address currently matches a non-deleted user with status ACTIVE or PENDING_VERIFICATION and an existing password hash. All six platform roles follow the same rule, including ADMIN/SUPER_ADMIN. Do not change role, `roleVersion`, status, email, verification flag, farm/onboarding state or entitlements. Recheck eligibility both at issuance and at consumption, under the user lock for writes.

The worker generates **32 cryptographically random bytes**, encoded as 64 lowercase hex; store SHA-256 of `password-reset:` plus token. Lifetime is **30 minutes from issuance**, using database timestamps for final expiry checks. Bind each credential to user ID, HMAC of the normalized registered email and the current `authorizationVersion`. The credential is invalid after any bound value changes, after `expiresAt <= database_now`, or after consumption/invalidation. Requests never extend existing credentials. Each admitted request is processed once; worker retries reuse its existing credential instead of minting another.

Completion: apply abuse limits, read the hash-matched credential and user snapshot, reject invalid/ineligible states, then compute the bcrypt-12 hash outside the transaction. In one transaction lock user → its outstanding credentials in ID order → affected recovery jobs in ID order; recheck current password/version/email/eligibility and database time. Atomically update password, increment **authorizationVersion only**, revoke all refresh tokens, consume this credential, invalidate remaining credentials, cancel obsolete reset-link jobs/erase their ciphertext, append `PASSWORD_RESET_COMPLETED` audit and insert one durable password-changed notification job. Audit/notification-intent failure rolls everything back. Audit metadata contains only purpose, safe record IDs and resulting authorization version; never password hashes, address/token hashes, ciphertext, raw IP/email, secret values or provider bodies. No new public/admin notification-history projection is introduced. Do not perform mail/network I/O inside this transaction.

Concurrent completions (same or different links) admit one winner; the loser sees `RESET_LINK_INVALID`. Login's existing password-snapshot/user-lock check prevents an old-password session created after the reset commit; refresh locking prevents rotation from escaping revocation. New and legacy access claims fail the next current-identity check after commit. Recheck HTTP guards and [active/passive consultation sockets](../../../apps/api/src/modules/consultations/gateways/consultation-chat.gateway.ts); revocation does not retract already completed responses or external provider capabilities.

On confirmed completion the BFF clears this browser's access/refresh cookies, even if it was signed into another account, and the client serializes the mutation with `withSessionLock` and broadcasts the existing auth logout/revalidation event. Server revocation targets only the recovered user. No new session is issued. A lost acknowledgement must not auto-resubmit: offer normal sign-in with the just-entered password or a fresh link; replay remains invalid.

## Abuse, trusted origin and secrets

Required default budgets, applied atomically in shared Redis before account lookup: request **20/IP/15 min** and **500/global/minute**; per normalized email **one admitted request/60 seconds** and **three/hour**, silently coalescing excess to generic 202. Complete **30/IP/15 min**, **60/global/minute** and **five/token hash/15 min**. Email/token budgets are applied equally to unknown identifiers. No account lockout or password/session mutation from abuse counters. Failure to enforce counters returns 503, with no issuance/reset.

The 500/minute global budget is an abuse ceiling, not a delivery-capacity promise. Before address-specific suppression, apply account-independent SQL admission backpressure: at most **100 unfinished RESET_REQUEST jobs**, and reject new admission with 503 while the oldest unissued request is **60 seconds** old or more. Serialize count/check/insert with a transaction-scoped admission lock so concurrent requests cannot exceed the cap; never inspect the submitted address/account for this decision. Notices bypass this request-admission cap so reset completion is not blocked by intake saturation. Target load acceptance must establish a sustainable rate/worker count and lower the global budget if needed; do not claim 500/minute sustained throughput from these defaults.

Use HMAC-SHA256 with `HASH_PEPPER` and separate `recovery-email` / `recovery-ip` / `recovery-token` domains for Redis identifiers; no raw emails, addresses or tokens. Reuse fixed-window limiter mechanics, but explicitly distinguish silent address suppression from public limits. Recovery address resolution defaults to the socket peer. Honor forwarded chains only behind explicitly configured trusted proxy CIDRs; never accept the first arbitrary forwarded value. The web ingress adapter must supply a verified client address, or fail closed in production. A shared BFF/socket address must not silently be presented as per-user protection. Trusted topology/client-budget acceptance is a release gate; other endpoints' ClientMeta behavior is unchanged.

Build links only from validated canonical `WEB_BASE_URL` origin, fixed `/reset-password` and `#token=<token>&locale=<bn|en>`. Production requires HTTPS, an origin-only URL without credentials/query/fragment, and no loopback; HTTP is restricted to explicit nonproduction loopback tests. Never use Host/forwarded-host/request data. GET/page previews/link scanners do not consume credentials.

The reset client reads the fragment into tab memory, immediately replaces history with the token-free same path, and never stores token/password in local/session storage, persisted state, cookies, analytics, error reports or DOM hidden fields. Apply no-referrer/no-store/noindex headers/metadata; no third-party scripts, tracking pixels or reset-link click rewriting. Token loss on reload/new tab after stripping leads to the missing-link state; it is not recovered through browser persistence. Switching reset-form language changes in-memory copy without a server redirect; after success normal locale persistence is safe. Keep sign-in/sign-up modal behavior intact.

## Persistence and worker contract

Two additive API-schema models; names below are planned. No root Prisma tree edits, old-row rewrite or applied-migration changes.

- **PasswordResetCredential:** UUID PK, user FK, unique 64-character token hash, 64-character email HMAC, authorization-version snapshot, created/expiry/consumed/invalidated timestamps. Index `(userId, expiresAt)`; lifetime/terminal-state/check constraints. No recoverable token here; do not impose one-outstanding-token uniqueness.
- **AccountRecoveryJob:** UUID PK, kind RESET_REQUEST or PASSWORD_CHANGED, nullable user/credential FKs (credential link unique), locale, email HMAC, nullable AES-GCM payload, immutable template/origin version and purpose-keyed HMAC of the exact provider payload, created/deadline/available/lease timestamps, random lease-fence UUID, attempts, terminal status and bounded failure code. Pending request payload is encrypted normalized email; issuance replaces it atomically with an encrypted envelope binding job ID, credential ID, email HMAC, origin/template version and token. Password-changed payload has no token. Index due unfinished jobs and user/credential references; require terminal jobs to have null payload. Unknown/ineligible jobs never acquire a credential/user link and erase their payload when skipped.

Use the existing PII crypto service for encryption, checking embedded context IDs and token hash after decryption to prevent ciphertext swapping. The separate worker claims at most **two available jobs**, with **60-second fenced leases**, sends at concurrency at most two and immediately refills free slots while due work exists; **five seconds** is idle polling backoff only. When both job kinds are due, reserve one slot for each kind; borrow idle capacity otherwise. Multiple worker instances share SQL claims and admission backpressure. Claim transactions hold only job locks and commit before user/credential operations; business mutations use user-first ordering. Workers must verify the fence before state changes; stale completions cannot overwrite a restarted worker. Never hold a DB transaction during remote sending. A request not processed within **10 minutes** is skipped/erased; an issued reset job cannot outlive its credential. Password-changed notice deadline is **24 hours**.

Transport timeout **10 seconds**; at most **five total attempts**, retry delays **5/30/120/600 seconds**, never beyond the deadline. Recheck current account/email/version and credential state immediately before each reset send. Use fixed failure codes, not raw provider messages. Terminal link failure invalidates its credential and erases encrypted payload; notification failure never reverses a committed password reset. A send racing expiry/reset can deliver an unusable link; consumption remains authoritative.

Initial production adapter: dedicated recovery Resend sender using configured `RESEND_API_KEY` / `EMAIL_FROM`, fixed API destination and `Idempotency-Key: recovery/<job UUID>`. Retries preserve the exact rendered recipient/body/subject/from/template/origin bytes; configuration drift fails the job safely rather than changing a payload under the same key. Status ACCEPTED means provider acceptance, not receipt. Scoped transport returns explicit REAL versus TEST outcome and fixed error code; production forbids mock/simulated modes and cannot fall through to SES simulation. Local test mode must be explicit and configuration-rejected in production. Do not call the current generic Resend logger with sensitive payloads; no raw provider bodies/addresses/link tokens in recovery logging.

Erase payloads immediately on terminal outcomes and sweep expired credentials/pending ciphertext at least every minute in the worker. Delete terminal job/credential metadata after seven days, preserving immutable minimal audits; expired credentials are unusable even if cleanup is delayed. Coordinate encryption-key rotation with the queue drain/expiry window; don't rotate/reset existing PII keys for this feature. Disable the feature and invalidate outstanding grants if confidentiality is lost.

## UI and acceptance

Forgot password is an internal request panel of the existing sign-in dialog, preserving AuthProvider's login/register mode contract and protected-entry behavior. Clear password on entering/leaving recovery, retain email only in dialog memory, support Back to sign in, labelled email, pending disablement, generic acknowledgement, rate-limit and unavailable/retry states. No control is enabled until API/local acceptance and the deployment feature flag permit it. Acknowledgement never claims delivery or reveals eligibility.

Public `/reset-password` offers valid-fragment password/confirmation, missing/malformed-link, generic expired/used/invalid-link, validation, pending, uncertain failure, retry guidance and success states. No automatic validation/POST on mount. Both locales, keyboard focus/errors and 320/1440px; same Tailwind/auth foundations. Explain password length failures plainly; do not display hashing implementation details. Successful reset offers normal modal sign-in, retaining safe locale selection; no return/callback URL is accepted. New-password confirmation is never persisted or sent to the API.

Acceptance matrix: strict API/BFF shapes/methods/origin/byte limits; identical request acknowledgement for all roles/statuses/unknown addresses; spoofed forwarding, all counters and Redis failure; no plaintext in DB/Redis/logs/URL requests; entropy/hash/expiry/address/version binding; same/different-link races; audit rollback; concurrent login/refresh/privilege change; old password and old/new-format access/refresh denial after a distinct replacement; active/passive socket checks; worker crash/lease/fence/retry/decryption/expiry; no simulation accepted in production; lost acknowledgement; host injection; link scanning; fragment stripping/language/session-tab races; full bilingual request/reset browser flow. Exact commands and migration/provider gates are in the plan.

## Guidance and release boundary

The general design follows [OWASP Forgot Password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html): neutral disclosure, bounded attempts, expiring single-use credentials, normal sign-in after reset and session invalidation. The concrete lifetimes, budgets, SQL worker and locale/browser contracts above are project decisions. [Resend's idempotency documentation](https://www.resend.com/changelog/idempotency-keys) describes 24-hour key retention; [its tracking description](https://resend.com/blog/open-and-click-tracking) explains redirect rewriting. Disable tracking for the chosen transactional domain and verify delivered fragment URLs intact; do not infer provider configuration from these references.

Feature configuration defaults **off**. Before enabling: apply/rehearse the additive migration with populated backup/restore and schema parity; run local API/persistence/worker/BFF/browser acceptance; verify canonical target origin/proxy budgets; prove real configured Resend delivery, intact fragment links and password-changed notice in authorized test inboxes; demonstrate persistent worker restart/retry and operational ownership. Sending to external recipients, production migration and deployment remain separate authorized actions. Rollback disables public controls/API admission and stops new jobs, invalidates outstanding credentials/erases secret payloads, and retains additive tables and completed password/version/session/audit writes. Never restore old passwords or active sessions to undo a release. A disaster/PITR restore is a separate maintenance event: keep auth/recovery traffic and workers disabled, invalidate all restored reset credentials, erase restored job payloads, revoke refresh tokens and rotate the access-signing secret before reopening. A restored authorization-version increment alone can collide with a previously issued version and is not sufficient. Reconcile any password changes lost by the restore under the incident runbook; backups do not automatically preserve later credential consumption.
