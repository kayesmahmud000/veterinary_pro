## Advisory triage

Observed installed production dependencies include Next **14.2.35** and proxy-addr **2.0.7**. Registry advisories are version matches, not exploit demonstrations. The critical findings require these distinctions:

- [Next Windows filesystem RCE](https://github.com/advisories/GHSA-p293-qw3h-jr36): the advisory describes affected Windows-hosted applications; this acceptance host uses Linux. The actual release filesystem/runtime must be verified. The registry's first patched major line is 15.5.24.
- [Next AVIF image-optimization RCE](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4): concerns AVIF processing through sharp/libheif. This local build warns that optional sharp is absent. That does not establish the deployed image-processing binding or dismiss the other Next advisories.
- [proxy-addr mapped-IPv6 trust subnet spoofing](https://github.com/advisories/GHSA-jqcg-44mw-7w3h): requires the affected proxy-trust configuration. No `trust proxy` setup was found in API source during this review; target proxy/middleware behavior remains unverified. The advisory identifies 2.0.8 as patched.

Additional high findings include Next server-action/RSC/rewrites, Multer multipart denial of service and SheetJS parsing issues. Review the saved full registry report and real route exposure rather than treating a missing prerequisite for one critical advisory as clearance for all 54. A Next major upgrade or replacement spreadsheet parser is a separately scoped compatibility change; no dependency/lockfile was silently changed during acceptance. Advisory metadata is time-dependent; rerun before release.

## Ordered rollout

These are prepared steps, not executed deployment commands. The release owner must first name the target and confirm release authorization; the database operator must verify the selected URL points to that target without printing credentials.

1. Record the reviewed source diff/immutable build identifier, API/web/worker versions, hosting configuration, current migration ledger and previous API/web/worker rollback targets. Resolve the open security and integration gates above. Verify persistent hosting for BullMQ, schedules, FFmpeg and realtime features actually enabled in this release.
2. Quiesce incompatible writers and new managed-media/notification retry requests. Inventory open uploads, retained failed jobs, pending outbox/deliveries and financial/clinical writes. Take a consistent database backup plus object inventory and configuration/version records; restore to a separate isolated target and verify representative data and migration checksums. A backup file without a successful restore is insufficient.
3. Against the confirmed target, inspect `pnpm --filter @vetralink/api exec prisma migrate status`. Apply only committed pending migrations with `pnpm --filter @vetralink/api db:deploy`. The active schema is `apps/api/prisma/schema.prisma`; never use the differing root schema, migrate dev/reset or db push. ADM-7 `20261019100000_admin_communications` and ADM-8 `20261019160000_admin_platform` must precede their new code. Verify the actual ledger; do not assume only these two remain pending.
4. Deploy the API candidate retaining current identity/privacy/managed-media protections. Deploy generation-aware role-notification workers and compatible domain/media workers on their persistent hosts; ensure all instances agree on database and Redis namespace. Do not let workers for different databases consume the same queue namespace. Verify the emitted `dist/main.js` and `dist/role-notifications.worker.js` entry points and shutdown behavior.
5. Confirm actual database/Redis readiness, queue registrations/backlogs and bounded probe responses. Deploy the web candidate only after its API contracts are available. Resolve API_BASE_URL to the intended `/api/v1` upstream; test through same-origin BFF routes.
6. Run the smoke matrix below. Enable only accepted workflows, monitor the named thresholds/backlogs and retain trace/job IDs with secrets, recipient data, medical payloads and signed URLs excluded. Release approval requires recorded outcomes and owner sign-off, not this prepared checklist.

## Recovery

- Stop new affected requests and restore the previously reviewed compatible web target first where appropriate. Keep the API safeguards required by existing managed assets and current identity versions. Pre-ADM-3 API code can reintroduce legacy media bypasses; it is not a safe automatic rollback target.
- Retain additive communications/platform/course/media tables and append-only audits. Older compatible application code may ignore additive records. Do not drop tables or rewrite applied migration history to roll back a screen.
- Keep generation-aware workers while pending retries drain, or stop dispatch for supervised forward recovery. Preserve failed generation-zero job IDs and durable generations; an older dispatcher can collide with retained jobs and strand newer retries. Reconcile an ambiguous external send before replay.
- Restore a production backup only under an explicit data-recovery decision after accounting for writes since the backup, object state, provider actions, immutable clinical/financial records and queue/outbox state. The local 24→29 restore rehearsal proves a disposable path, not the target's recovery point/time objectives.
- After recovery, rerun readiness/auth/role/privacy and affected real-user-path checks; record actual target versions, reconciliation results, monitoring and remaining disabled workflows.
