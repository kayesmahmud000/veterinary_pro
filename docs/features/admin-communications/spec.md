# ADM-7 — Public content, notification history and support

Selected 2026-10-19 by “go with next pending”, following completed local ADM-6. Parent: [administration roadmap](../../../apps/web/ROADMAP.md#admin-and-super-admin-delivery-roadmap), product blueprint public education/veterinary/support scope. This specification defines the missing API-ADMIN-C/N contracts; it does not authorize a deployment or external message.

## Result and boundaries

ADMIN/SUPER_ADMIN can manage bilingual blog, page, FAQ, guide and veterinarian directory entries; inspect safe delivery history and request eligible role-email retries; and handle account-scoped support tickets. All active accounts can open and read their own support conversations. Public readers see an explicitly published snapshot only. Existing authored articles/guides/demo doctors remain available and cannot be shadowed by CMS slugs. Clinical records, payments, membership, entitlements, broadcast mail and provider controls are outside this batch.

## Content contracts

`GET/POST /api/v1/admin/content`, `GET /admin/content/:id`, `POST /admin/content/:id/save`, `POST /admin/content/:id/actions`. Strict shared Zod inputs; UUIDs canonicalized. Lists use ascending UUID keysets, limit 1–20, optional kind/search/cursor. Five kinds: BLOG, PAGE, FAQ, GUIDE, VET. Slug/kind/subject identity are immutable after creation. Both languages have title (1–200), summary (0–600), body (0–20000). Save permits incomplete body; publish requires nonempty summary/body in both languages. Text is plain text, escaped by React, with no HTML, Markdown, embedded media, external fetch or authored URL support. Reject control characters, preserve newlines. Preview renders the draft through the same text renderer as public content. Save creates an immutable numbered revision and leaves the public snapshot unchanged. Publish copies the current complete draft to the public snapshot; unpublish clears it. A version check covers every mutation; publishing already-current or unpublishing absent content fails with a reloadable conflict. At most 20 private revisions are returned, with truncation indicated.

VET entries require an existing active VET user and a nonempty VetProfile license. Publishing additionally requires explicit qualification/identity verification confirmation and a private verification note (10–1000 chars), recorded in the atomic audit. The public snapshot is bound to the subject's current authorization version. Public reads require that same version and active VET status, so suspension, deletion or role changes hide publication immediately. This publishes a curated biography, not a license number, contact details, clinical record or availability promise. One VET entry per subject. Admin edits cannot modify the underlying account/qualification.

`GET /api/v1/content/:kind` (limit/cursor/search), `GET /content/:kind/:slug` return only id/kind/slug, bilingual published text, publication time and a verification flag for VET. No draft, revision, actor, subject user ID or verification note is public. Public pages use no-store reads; unavailable API is visibly distinct from empty/missing results. New entries appear on existing blog/doctor discovery and `/pages`, `/guides`, `/help` (FAQ). Static legacy slugs are reserved; no source content is silently overwritten. New CMS entries use `/blog/:slug`, `/doctors/:slug`, `/pages/:slug`, `/guides/:slug`, `/faq/:slug`.

## Notification contracts

`GET /admin/notifications` lists one explicitly selected source (ROLE_EMAIL or CONSULTATION), 1–20 ascending UUID keyset records and optional recognized status. Safe projection includes ID, recipient display identity (redacted on deletion), channel, event category, timestamps, attempt count, revision and retry availability. Never expose email/phone, body/title, provider message IDs, raw errors, private role-review or clinical content. Role SENT means provider accepted, not recipient delivery; consultation SENT is explicitly an unverified domain record because current SMS/push providers may be mocks.

`POST /admin/notifications/:id/retry` supports only terminal FAILED role-email deliveries to a still-active eligible recipient and nonobsolete event. Password/reason/confirmation and expected generation are required. The transaction resets the delivery to PENDING, increments a retry generation, reopens the durable outbox and writes audit atomically. Dispatcher job IDs include generation, avoiding retained failed-job collisions. Old-generation completion/failure cannot overwrite a newer generation. Existing automatic retry and recipient authorization are retained. No retry for accepted/skipped/pending or consultation records, and no synchronous provider dispatch. UI explicitly warns that acceptance is not delivery and retry after an uncertain provider failure can duplicate an email.

## Support contracts

`GET/POST /support/tickets`, `GET /support/tickets/:id`, `POST /support/tickets/:id/messages` require current active identity, own requester only. Create takes client-generated UUID, subject (5–160), category ACCOUNT/FARM/ORDER/OTHER, initial plain text (1–4000), optional farmId/orderId; linked farm must have actual current membership, order must belong to requester. Duplicate create ID is a conflict, never a duplicate ticket. Own replies require expected version, open status, client-generated message UUID and public text. No clinical attachments or automatic outgoing message is created.

`GET /admin/support`, `GET /admin/support/:id`, `POST /admin/support/:id/actions` require ADMIN/SUPER_ADMIN. Queue filters: status/search/cursor/limit. Detail returns safe requester/assignee identity, account/farm/order references, last 50 messages and truncation marker. Actions use expected version, password/reason/confirmation: ASSIGN (active administrative assignee or unassign), STATUS (OPEN/IN_PROGRESS/WAITING/RESOLVED/CLOSED), REPLY (requester-visible or private internal note). Closed tickets reject replies; reopening is an explicit status action. Requesters never see internal notes or admin action reasons. All writes and audits are atomic; support access grants no farm membership, medical data or financial write access. A reply is visible in the in-app conversation; it does not imply email/SMS dispatch.

## Shared safeguards and acceptance

Current-primary identity/version checks precede protected reads; writes lock/recheck actor, then subject/ticket/document/delivery in a consistent order. ADMIN/SUPER only on administrative routes and BFF, same-origin writes, exact method/path/query/body allowlists, bounded bytes, no private cache. Sensitive admin actions require password, reason, explicit confirmation and fail-closed rate limiting. Versions prevent stale/repeated writes; audit failure rolls back the write. Browser writes bind to displayed actor ID/role/authorization version; changed identity discards drafts, revalidation clears secrets, recoverable failures retain nonsecret input, uncertain writes require reload.

Acceptance covers strict input/output projections, wrong-role/foreign-ticket denial, draft/public separation, plain-text injection safety, bilingual completeness, stale/duplicate writes, vet eligibility changes, safe notification statuses/generation retry, internal-note privacy, support links, rollback and migration rehearsal. Web uses existing workspace components and Tailwind only, Bangla default/English selectable, keyboard labels, 320px/1440px layouts, explicit loading/empty/error/retry/success states. Builds/tests/browser evidence must state controlled providers and unavailable live database/provider acceptance separately.

## Persistence and recovery

Add EditorialDocument, EditorialRevision, SupportTicket and SupportMessage tables and role-delivery retryGeneration to the active API schema, with bounded keys, FK preservation, version/default/check constraints and query indexes. No old row is rewritten or old migration changed. Rehearse new migration on explicitly disposable PostgreSQL with representative old rows; production rollout requires backup/restore and migration before code. Revert code while preserving additive tables for recovery; do not drop authored/support data. No offline/mobile protocol or financial model changes.
