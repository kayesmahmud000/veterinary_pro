# Current role/authentication architecture and findings

Status: **Historical pre-implementation investigation, 2026-10-07.** The five-role observations below describe the writing-time baseline; they are superseded by the implemented [backend plan](backend-plan.md), [frontend plan](frontend-plan.md) and [verification/runbook](operations.md). Implementation was later authorized and completed locally.

Date: 2026-10-07. HEAD: `9db3062` plus existing uncommitted modal authentication work. **Confirmed from code** below means source inspection, not exploitation testing, live database observation or deployed readiness.

## Architecture traced

| Boundary | Current implementation and evidence |
| --- | --- |
| Roles | [Shared enum](../../../packages/shared-types/src/enums/index.ts) and [active Prisma schema](../../../apps/api/prisma/schema.prisma) contain SUPER_ADMIN, ADMIN, VET, FARMER, BUYER. LEARNER is absent. The backend is a five-role system, with three public registration choices. |
| Registration transport | [RegisterDto](../../../apps/api/src/modules/auth/dto/register.dto.ts): required email, name 2–100, password 8–128; optional string phone; optional role validated against the five-role enum. Global ValidationPipe in [main](../../../apps/api/src/main.ts) and [serverless](../../../apps/api/src/serverless.ts) whitelists and rejects unknown fields. |
| Registration service/storage | [AuthService.register](../../../apps/api/src/modules/auth/services/auth.service.ts) defaults to FARMER, rejects ADMIN/SUPER_ADMIN and immediately accepts FARMER/VET/BUYER. [UserEntity.create](../../../apps/api/src/modules/users/entities/user.entity.ts) and the schema also default to FARMER. Email/phone uniqueness, bcrypt password hashing, encrypted phone/blind index and transactional user/refresh-token creation are present. |
| Login | [LoginDto](../../../apps/api/src/modules/auth/dto/login.dto.ts) requires email/password; phone and rememberMe are optional. AuthService.login looks up stored identity, checks password and suspended/deleted state, then issues tokens from the stored role. No three-role login allowlist exists; all five current valid roles can pass this role aspect of login. Actual six-role login is impossible until LEARNER is added. |
| JWT/session | [TokenService](../../../apps/api/src/modules/auth/services/token.service.ts) signs access JWT with sub/email/role/status/jti and optional activeFarmId; validates signature/expiry. No runtime decoded-claim schema or live authorization lookup exists there. Defaults: 15-minute access and seven-day opaque refresh, configurable. Refresh hashes/rotation/reuse detection are implemented. |
| HTTP authentication | [JwtAuthGuard](../../../apps/api/src/common/guards/jwt-auth.guard.ts) verifies the bearer token and assigns its decoded payload directly to request.user. It does not reload current user role/status/deletion. Guards are applied per route/controller, not globally to all endpoints. |
| Role guard | [RolesGuard](../../../apps/api/src/common/guards/roles.guard.ts) checks @Roles against the JWT role and token status. No role metadata returns true. SUPER_ADMIN bypasses every declared role list. Merely attaching RolesGuard without @Roles does not restrict role access. |
| Tenant guard | [TenantGuard](../../../apps/api/src/common/guards/tenant.guard.ts) resolves farm ID, checks farm membership and FarmRole; SUPER_ADMIN bypasses membership. It does not block an unapproved global role. Farm membership is independent of platform role. |
| Current user | [AuthController](../../../apps/api/src/modules/auth/auth.controller.ts) exposes register, login, refresh, logout, logout-all and me. GET me reloads stored identity and blocks suspended/deleted users, then returns an explicitly selected summary. No user role-management/profile-write endpoint exists in [UsersModule](../../../apps/api/src/modules/users/users.module.ts), which currently exports a repository only. |
| Mutation repositories | [UserRepository.update](../../../apps/api/src/modules/users/repositories/user.repository.ts) writes the complete entity including role/status/password hash. Login calls it to record last-login time. The entity has no controlled changeRole method or optimistic role version. Transaction interfaces support an explicit isolation level. |
| Administrative features | Existing admin routes manage products, plans/dunning/metrics, triage/assignment, settlement/review and support actions. No application-review or privileged-account-management controller/model exists. Several domain services repeat role checks outside RolesGuard. |
| Clinical roles | [PrescriptionService.verifyDoctorWriteAccess](../../../apps/api/src/modules/consultations/services/prescription.service.ts) currently permits an assigned VET or ADMIN/SUPER_ADMIN. Read paths check participant/membership. [VetAssignmentService](../../../apps/api/src/modules/consultations/services/vet-assignment.service.ts) can synthesize an available profile for an existing VET without a profile; role alone is not qualification verification. |
| WebSocket | [ConsultationChatGateway](../../../apps/api/src/modules/consultations/gateways/consultation-chat.gateway.ts) verifies JWT once on connection and retains its payload in socket data. Join/send/read paths use that retained identity; typing does not repeat participant authorization. There is no current live role/session invalidation mechanism for already-joined listeners. |
| Mail | [MailModule](../../../apps/api/src/modules/mail/mail.module.ts) binds Resend/SES/mock from config. Generic MailService.sendEmail is reusable. MailQueueService and MailProcessor are typed/wired to order-delivery jobs only. Mock is the config default; generic send capability is not a role-request notification system. |
| Web auth | [Contracts](https://github.com/kayesmahmud000/veterinary_pro/blob/dev-fontend/apps/web/src/lib/auth/contracts.ts) accepted five returned roles, defaulted signup to FARMER and accepted three PUBLIC_ROLES at investigation time. [AuthDialog](https://github.com/kayesmahmud000/veterinary_pro/blob/dev-fontend/apps/web/src/components/auth/auth-dialog.tsx) rendered the three-role signup selector. [Server boundary](https://github.com/kayesmahmud000/veterinary_pro/blob/dev-fontend/apps/web/src/lib/auth/server.ts) forwarded a fixed auth allowlist and stored tokens in HttpOnly cookies. [Provider](https://github.com/kayesmahmud000/veterinary_pro/blob/dev-fontend/apps/web/src/components/auth/auth-provider.tsx) restored identity/refreshed and coordinated tabs without application/admin UI. These links point to the owning frontend branch; the baseline descriptions are historical. |
| Mobile/root schema | Flutter main UI is a placeholder; its sync library consumes bearer auth but has no inspected complete login/signup UI. API package selects apps/api/prisma/schema.prisma. Root prisma/schema.prisma is a divergent schema/migration lineage and must not be treated as the active migration target. |

## Findings and implications

| Finding | Evidence classification | Consequence / planned response |
| --- | --- | --- |
| Signup directly grants professional roles and defaults to FARMER | Confirmed from code: AuthService.register | Latest user policy retains explicit FARMER/VET/BUYER signup; change omitted-role default to LEARNER in service/entity/schema/UI and keep strict administrative-role rejection. |
| LEARNER absent in shared/schema/web validators | Confirmed from code | Adding only one enum would leave default/validators/labels/session parsing inconsistent; update the full flow together. |
| Old signed role/status claims remain authorization inputs | Confirmed from code: guards and gateway | Likely behavior: existing genuine tokens can retain authorization until expiry after a role/status change on routes lacking live checks. Test this before/after the fix; do not confuse it with forged JWT acceptance. Signature verification already rejects edited unsigned claims. |
| Generic user updates can overwrite a concurrent role decision | Confirmed write path: login loads entity then UserRepository.update writes its role | Likely race after introducing role mutations. Separate lastLogin/profile writes from privilege writes and lock/recheck the current identity before token minting. |
| Duplicate/racing requests and decisions have no persistence model | Confirmed absence of role-request workflow in inspected modules/schema | Add unique pending-request constraint, immutable terminal decisions, expected versions and transactional approval/audit. |
| Tenant-only routes are not global approval gates | Confirmed from code: farm/animals/milk/clinical/financial controllers | LEARNER must not obtain professional operations merely through membership. Preserve existing approved-role staff access and all farm/subscription checks. |
| SUPER_ADMIN generic bypass is too broad for LEARNER-only requests | Confirmed from code: RolesGuard | Use exact role checks; explicitly preserve existing intended administrative permissions, with domain checks. |
| OrdersController has RolesGuard but no @Roles on checkout | Confirmed from code: OrdersController | Checkout currently uses authenticated purchase policy. Preserve it for LEARNER learning purchases; do not incorrectly describe it as BUYER-only authorization. |
| Order download-token admin check is inconsistent | Confirmed from code: OrderFulfillmentService.getDownloadTokens checks ADMIN only; other download/resend paths include SUPER_ADMIN | Small in-scope permission correction with ownership and both-admin tests; do not let a role list hide service-level exclusions. |
| Direct VET signup does not establish verified qualifications | Confirmed from code: direct VET registration; optional VetProfile license | Latest policy continues direct VET signup. Manual verification/unavailable profile applies to the reviewed upgrade path only; do not certify all VET accounts or invent approval provenance. |
| Mail jobs are order-specific; no durable role event/outbox exists | Confirmed from code | Separate role queue/processor, reuse provider adapters, commit outbox with business decision and verify restart/retry delivery. |
| Session/token concurrency needs backend protection | Confirmed from code: refresh eligibility read before tx, then unconditional revoke/create | Likely race: concurrent rotations can both pass the precheck. Lock and conditionally consume refresh records; coordinate with privilege revocation. Browser Web Locks alone are insufficient across clients. |
| Email verification / phone-only login / rememberMe are incomplete | Confirmed from code: no auth verification/reset routes; email-required LoginDto; rememberMe unused | Preserve email/password journey. Do not present unimplemented features or require verification that cannot be completed. Separate unrelated remediation. |

## Investigation limits
